Application Entry

app_main

这是当前 C++ 层真正已经接入的应用入口，但它现在只负责“把 CLI 调试链路接起来”，不代表完整飞控应用层已经组装完成。

核心文件

  • iFly/app_main.cpp
  • iFly/app_main.h
  • Core/Src/main.c

职责

初始化 HardwareUart(UART5)、UsbUart 和 FlightCtrlCli，注册两条 transport，默认切到 usb，然后进入一个极简轮询循环。

当前真实运行步骤

  • InitCliRuntime() 里先初始化 USB/UART，再初始化 CLI，并注册 uart5、usb 两个通道。
  • 初始化完成后先 DelayMs(20)，再立即做一次 Poll()。
  • 随后启动一个 tick::NonBlockingDelayMs，每 50 ms 轮询一次 CLI。
  • 主循环底部仍保留 DelayMs(1)，所以现在没有任务派发器，也没有飞控业务闭环。

代码阅读入口

  • 先看 InitCliRuntime()，确认当前真正接入了哪些模块。
  • 再看 kCliPollPeriodMs 和 cli_poll_delay，理解 CLI 不是每圈都跑，而是 50 ms 一次。
  • 最后看 while (1)，明确当前主循环里还没有 TaskManager::Dispatch() 或控制链路。
当前状态

已接入，定位为当前调试装配入口。

CLI Runtime

FlightCtrlCli

它把 Shell、参数管理、PID 样例和 transport 选择绑成一个可直接用于板上调试的运行时壳层。

核心文件

  • iFly/app/cli/flight_ctrl_cli.hpp
  • iFly/app/cli/flight_ctrl_cli.cpp

底层原理

本质上它不是再造一套 Shell，而是围绕飞控调试场景，给通用 Shell 叠加 transport 绑定、参数表、函数表、欢迎输出和运行时状态维护。

用到的技术

  • 固定容量 transport 注册表，避免动态分配。
  • 通过 RegisterParameters() 把 PID、系统频率、锁定状态等统一暴露给 Shell。
  • 通过参数更新回调把 pid.* 变化即时同步到 Pid 实例。
  • 通过 RegisterFunctions() 注册 status、pid.sample、transport.use 等调试入口。

代码阅读入口

  • 先看 Init()，确认 Shell、参数和函数的装配顺序。
  • 再看 RegisterTransport() / UseTransport()，理解通路切换如何生效。
  • 最后看 Poll() 和命令回调，理解 CLI 运行时是怎么被主循环驱动的。
当前状态

已接入。它是当前仓库里最完整、最真实、也最容易验证的 app 层装配模块。

Interactive Console

Shell

Shell 负责真正的会话状态机、命令分发、参数读写和函数调用，是 CLI 体验的底层核心。

核心文件

  • iFly/lib/shell/shell.hpp
  • iFly/lib/shell/shell.cpp

底层原理

内部维护多阶段会话状态: 未连接、激活提示、会话动画、密码输入、可交互态。所有输入字节先经过状态机，再决定是回显、拼命令、执行命令还是忽略。

用到的技术

  • 按字节处理输入，支持回车、退格、打印字符和激活键。
  • 固定容量命令表、函数表、参数表，适合嵌入式无堆或少堆场景。
  • 内建命令模型统一了 help、func、param 以及快捷别名。

代码阅读入口

  • 看 Poll()，了解 Shell 如何从 transport 中取字节并推进状态机。
  • 看 ProcessByte()，理解字符级输入解析。
  • 看 ExecuteBuiltin() 和参数命令处理路径，理解命令体系如何落地。
当前状态

已接入。当前 CLI 的登录、提示、参数命令和函数命令全部依赖它。

Parameter Registry

ParameterManager

它负责把业务变量直接映射成 Shell 参数，省掉每个变量手写 getter/setter 和命令胶水的重复劳动。

核心文件

  • iFly/app/paramete/parameter_manager.hpp
  • iFly/app/paramete/parameter_manager.cpp

底层原理

内部把 float、u32、bool 等参数统一描述成表项，表项中直接保存业务变量地址，再由统一的解析/校验/写回路径处理。

用到的技术

  • 固定容量数组管理参数项，避免运行时碎片化。
  • 参数项直连业务变量地址，改值路径短，回写开销低。
  • 支持 on_updated 回调，适合参数变更后立刻刷新运行时配置。

代码阅读入口

  • 看 AddFloat() / AddU32() / AddBool() 如何登记变量。
  • 看 SetValue() 如何做字符串解析、范围校验和回调通知。
  • 看 RegisterToShell() 如何批量挂载到 Shell。
当前状态

已接入。当前 CLI 里的 pid.*、sys.loop_hz、sys.arm_locked 等参数都通过它暴露。

Controller Core

Pid

这是当前仓库里最成熟的控制基础件，也是已经和参数系统、CLI 样例计算打通的目标模块。

核心文件

  • iFly/app/ctrl/pid.hpp
  • iFly/app/ctrl/pid.cpp

底层原理

每次更新都会先清洗输入和 dt，再按配置选择微分源，依次完成导数滤波、积分更新、抗积分饱和判断和输出限幅，最终给出完整分量结果。

用到的技术

  • P / I / D / FF 各分量显式展开，便于调试和打印。
  • 支持多种微分模式，便于后续对测量值、误差或外部角速度建模。
  • 支持导数低通、积分限幅、输出限幅和异常数值回退。

代码阅读入口

  • 看 Configure()，了解配置清洗和边界矫正。
  • 看 Update()，理解完整单次控制更新路径。
  • 看导数滤波相关辅助函数，理解高频噪声如何被抑制。
当前状态

已接入，是当前最便于独立验证控制逻辑的模块之一。

State Distribution

ObserverChannel

这是一个面向“单发布者、多消费者”的无锁快照通道，可用于将姿态、估计值、遥控输入或状态快照安全分发给多个读取方。

核心文件

  • iFly/app/observer/observer_channel.hpp

底层原理

通道内部维护固定数量历史槽位和全局发布序号。发布时先把槽位标记成“写入中”，写入消息后再写入稳定戳；消费者只维护自己的 nextSequence，读取时自动判断是正常读取、无数据还是历史被覆盖。

用到的技术

  • 历史深度和最大消费者数量都通过模板参数固定，容量边界清晰。
  • Consumer 句柄自动占用/释放订阅位，避免额外注册表管理。
  • TryRead() 和 TryReadLatest() 区分“按序消费”和“直接取最新快照”。
  • 同一头文件里还提供了 CallbackConsumer 和 ObserverHub，方便把多个消息类型统一组织成观察总线。

代码阅读入口

  • 先看 Publish() / Emplace()，理解发布侧如何写稳定戳。
  • 再看 SubscribeLatest() / SubscribeFromNext()，理解消费者起始位置。
  • 然后看 TryReadImpl()，这是溢出检测和快照读取的核心。
  • 最后看 ObserverHub::BindLatest() / BindFromNext()，理解类型路由和回调封装。
当前状态

已实现但未接入当前 app_main()。它已经能独立使用，但还没有被串成真实应用层数据流。

Task Abstraction

TaskManager

它位于 SoftTimerService 之上，用“任务”而不是“底层软定时器句柄”来组织业务层定时逻辑。

核心文件

  • iFly/app/task_mage/task.hpp
  • iFly/app/task_mage/task.cpp

底层原理

每个上层任务槽位最终都会映射成一个底层 SoftTimerService 任务。触发后统一进入 TaskEntry()，再根据任务配置决定是周期重装、延后执行、挂起等待手动恢复，还是执行一次后删除。

用到的技术

  • 任务句柄由“槽位索引 + generation”编码，防止旧句柄误操作复用后的新任务。
  • 支持 CreatePeriodicTask()、CreateOneShotTask() 和完整 CreateTask() 配置入口。
  • 支持 DelayTask()、DelayCurrentTask()、SuspendTask()、ResumeTask() 等生命周期控制。
  • 运行中的任务如果请求删除或延时，都会延后到回调退出后统一处理，避免直接破坏当前执行栈。

代码阅读入口

  • 先看 CreateTask()，理解上层任务如何落成槽位和底层 timer。
  • 再看 TaskEntry()，这里是运行中删除、挂起、自动重装的核心汇合点。
  • 然后看 DelayCurrentTask() / ResumeTask()，理解任务生命周期控制。
  • 最后看 Dispatch() 和 Now()，确认它本质上仍依赖 SoftTimerService 驱动。
当前状态

已实现但未接入当前主循环。也就是说，任务抽象层已经具备，但 app_main() 还没有开始调 TaskManager::Dispatch()。

Time Base

tick / systick_time

时间系统分为两层: tick 提供面向 app 的统一接口，systick_time 负责真正的 HAL Tick 与 DWT 读时实现。

核心文件

  • iFly/app/tick/tick.hpp
  • iFly/app/tick/tick.cpp
  • iFly/lib/systick_timer/systick_time.hpp
  • iFly/lib/systick_timer/systick_time.cpp

底层原理

NowMs() 走 HAL_GetTick()；更高精度的 NowUs() / NowNs() 基于 DWT->CYCCNT；SysTick 中断还额外维护了 DWT 回绕的高位扩展。

用到的技术

  • 同时提供阻塞式 DelayMs() / DelayUs() 与非阻塞式 NonBlockingDelayMs / NonBlockingDelayUs。
  • C / C++ 双接口导出，便于和 HAL 生成代码一起工作。
  • 是当前 CLI 轮询、欢迎动画和各种时间统计的共同基础。

代码阅读入口

  • 看 NowMs() / NowUs()，理解不同精度的时间源。
  • 看 NonBlockingDelayMs::ConsumeIfExpired()，这是当前 app_main 50 ms 轮询的直接基础。
  • 看底层 DWT 相关代码，理解高精度时间的来源。
当前状态

已接入。当前已经跑起来的模块里，凡是涉及时间、延时和非阻塞轮询，基本都要经过它。

Software Scheduler

SoftTimerService

这是一个基于 SysTick 的轻量非抢占式软件定时调度器，也是 TaskManager 的直接底座。

核心文件

  • iFly/lib/soft_timer/soft_timer.hpp
  • iFly/lib/soft_timer/soft_timer.cpp
  • Core/Src/stm32f4xx_it.c

底层原理

SysTick 中断层只做 1 ms tick 递增，不直接执行任务；真正的任务执行要等主循环调用 Dispatch()，并按“已到期 + 优先级 + 创建顺序”选择任务，因此它是非抢占式调度器。

用到的技术

  • 固定 16 个任务槽位，不依赖运行期动态内存。
  • 支持 CreateTask()、DeleteTask()、DeleteAllTasks()、DelayCurrentTask()。
  • 保留了 C 接口 ifly_soft_timer_systick_tick()，方便直接从中断文件桥接。

代码阅读入口

  • 看 CreateTask()，理解底层任务槽位如何初始化。
  • 看 FindReadyTaskIndex() 和 Dispatch()，理解调度规则。
  • 看 DelayCurrentTask() 和删除逻辑，理解运行中任务如何安全改期或回收。
当前状态

已实现，但当前主循环没有派发它。所以它现在是“底座已就绪”，不是“已被应用层调度使用”。

Transport Abstraction

SerialIoBase

这是统一 USB、UART、CAN 上层使用方式的关键抽象层，也是 transport 能被 FlightCtrlCli 统一切换的前提。

核心文件

  • iFly/dev/serial_io_base.hpp

底层原理

它直接继承 DynamicLockFreeQueue，也就是说设备对象自己就是统一 RX 队列。Read() 会先调用 BeforeRead()，给派生类机会把底层暂存继续上抛，再真正出队。

用到的技术

  • 把统一 RX 队列直接塞进基类，减少层层封装。
  • EnsureRxQueueCreated() 允许在 Init() 阶段兜底创建动态队列。
  • 通过统一接口屏蔽了 USB/UART/CAN 底层差异，使上层只关心字节流读写与链路状态。

代码阅读入口

  • 看 Read() 的顺序: 先 BeforeRead()，后 Dequeue()。
  • 看 RxQueue()，理解底层服务为什么只拿一个 LockFreeQueueBase* 就能回灌数据。
  • 再回头看各个派生类如何复用这套抽象。

Reusable Primitives

double_buffer / freelock_queue

这些模块不直接暴露业务语义，但 USB、UART、CAN 等运行时服务能稳定工作，靠的就是它们。

核心文件

  • iFly/lib/double_buffer/double_buffer.hpp
  • iFly/lib/freelock_queue/lock_free_queue.hpp
  • iFly/lib/freelock_queue/lock_free_queue.cpp

职责

freelock_queue 提供静态/动态无锁环形队列；double_buffer 提供字节双缓冲和对象双缓冲，方便 DMA 或端点收发在“装载下一包”和“发送当前包”之间切换。

用到的技术

  • StaticLockFreeQueue / DynamicLockFreeQueue 共用同一个基础环形队列实现。
  • StaticByteDoubleBuffer 适合 UART DMA / USB 端点，StaticObjectDoubleBuffer 适合 CAN 帧这类定长对象。
  • 这些基础件是运行时服务层的共享依赖，不应该被写成某个单独模块的私有技巧。

代码阅读入口

  • 看队列的 Create() / Enqueue() / Dequeue()，理解统一收发缓存行为。
  • 看双缓冲的切换接口，理解为什么 DMA/端点发送路径没有直接拿业务缓冲裸跑。
  • 再回头看 UART / USB / CAN 服务如何组合使用它们。

UART Wrapper

HardwareUart

这是给上层使用的 UART 设备包装器，把逻辑串口号和统一 RX 队列对接到 UartDmaService。

核心文件

  • iFly/dev/uart_dev/hardware_uart.hpp
  • iFly/dev/uart_dev/hardware_uart.cpp

职责

对上暴露统一的串行 IO 接口，对下把当前对象自己的 RX 队列挂给指定 UART 端口，并把写请求转交给 DMA 发送服务。

实现要点

  • 初始化时先确保统一 RX 队列存在，再调用底层服务初始化端口。
  • 写入并不等待同步发送完成，而是进入底层 TX 队列。
  • 这层的价值在于把“哪个串口”变成构造参数，而不是让上层直接依赖 HAL 句柄。

当前状态

已接入，当前明确接上的只有 UART5 这条 CLI 备用通路。

UART Runtime Service

UartDmaService

这是真正处理多串口 DMA 收发、回调桥接、双缓冲装载和上层 RX 队列灌入的核心服务。

核心文件

  • iFly/lib/uart/uart_dma.hpp
  • iFly/lib/uart/uart_dma.cpp

底层原理

TX 路径是“上层写入 → TX 队列 → TX 双缓冲 → HAL_UART_Transmit_DMA()”；RX 路径是“DMA 缓冲 → 空闲中断回调 → 上层统一 RX 队列”。

用到的技术

  • 逻辑端口号到 UART_HandleTypeDef 的映射。
  • HAL_UARTEx_ReceiveToIdle_DMA() 用于接收到空闲事件的 DMA 读取。
  • 队列 + 双缓冲组合，降低连续发送时的阻塞和拷贝风险。
  • HAL 回调统一桥接到服务层，避免业务层接触中断细节。

代码阅读入口

  • 看 InitPort()，理解端口初始化和 DMA 接收启动流程。
  • 看 ServiceTxPath()，理解 TX 队列如何装载到 DMA。
  • 看 OnRxEvent()，理解新接收数据如何上抛给统一 RX 队列。
当前状态

已接入。它现在不仅服务 UART5，也已经是一套可扩展到多串口的通用运行时服务。

USB Wrapper

UsbUart

它和 HardwareUart 的定位类似，只不过底层介质换成了 USB CDC ACM。

核心文件

  • iFly/dev/usb_dev/usb_uart.hpp
  • iFly/dev/usb_dev/usb_uart.cpp

职责

把统一 RX 队列挂到 UsbCdcAcm，并向上提供和 UART 一致的串行字节流接口。

实现要点

  • Init() 时先创建 RX 队列，再将其附着到底层 USB 设备。
  • BeforeRead() 会主动调用底层 Service()，把设备暂存数据继续泵到上层队列。

当前状态

已接入，而且是当前默认 CLI 通道的上层包装入口。

USB Device Stack

UsbCdcAcm

这是当前仓库里最值得细看的底层模块之一。它不是简单套用一层现成中间件，而是自己实现了轻量 CDC ACM 设备层。

核心文件

  • iFly/lib/usb_cdc/usb_cdc.hpp
  • iFly/lib/usb_cdc/usb_cdc.cpp
  • Core/Src/usb_otg.c

底层原理

模块自己处理描述符、EP0 控制请求、CDC 类请求、IN/OUT 端点数据收发，以及与上层 RX 队列、TX 队列的衔接。

用到的技术

  • 基于 HAL PCD 的轻量设备适配层。
  • 端点双缓冲，提升持续收发稳定性。
  • 发送队列 + 端点缓冲 + HAL 回调桥接的组合。
  • 标准请求和 CDC 类请求的解析路径都在模块内部闭合。

代码阅读入口

  • 看 Init()，理解端点、缓冲和队列的初始化。
  • 看 OnSetupStage() / HandleGetDescriptor()，理解控制请求解析。
  • 看 ServiceTxPath() 和接收上抛路径，理解数据如何接到 app 层。
当前状态

已接入，而且是当前默认 CLI 通路真正工作的底层实现。

CAN Wrapper

HardwareCan

它的角色和 HardwareUart 相似，但同时保留了 CAN 按帧通信的语义，不把一切都伪装成普通串口。

核心文件

  • iFly/dev/can_dev/hardware_can.hpp
  • iFly/dev/can_dev/hardware_can.cpp

职责

对上仍兼容统一 IO 接口，对下则保留 WriteFrame() / ReadFrame() 这类更符合 CAN 使用直觉的接口。

实现要点

  • 仍复用统一 RX 队列，但数据单位是 CanFramePacket。
  • 兼容基类风格的 Write(data, len)，方便统一 transport 抽象。
  • 推荐上层真正使用时优先走帧语义接口，而不是手搓字节流。

当前状态

已实现但未接入当前主业务，是后续 CAN 链路装配的接口入口。

CAN Runtime Service

CanService

它负责把 CAN 的“按帧通信”适配进当前统一 IO 架构，同时桥接 HAL 接收 FIFO 和发送邮箱。

核心文件

  • iFly/lib/can/can.hpp
  • iFly/lib/can/can.cpp
  • Core/Src/can.c

底层原理

模块定义固定大小的 CanFramePacket 作为统一软件封包，这样上层虽可沿用统一读写风格，但底层不会丢掉 CAN 帧边界。

用到的技术

  • HAL CAN 回调桥接。
  • 固定帧封包、TX 队列和对象双缓冲。
  • 把标准帧、扩展帧、RTR、FIFO 来源等信息编码进 flags。

代码阅读入口

  • 看 CanFramePacket 定义，理解统一封包格式。
  • 看 InitPort()，理解过滤器和通知的启动流程。
  • 看收发回调桥接函数，理解 HAL 如何被抽离在服务层内。
当前状态

已实现但未接入主业务，而且当前硬件模式仍是 CAN_MODE_LOOPBACK，当前状态更接近“框架已准备好”。

Receiver Protocol

SbusProtocol

它负责从串口字节流中同步 SBUS 帧边界，并完成 16 路 11 bit 通道的解包与编码。

核心文件

  • iFly/app/proto/sbus/sbus_protocol.hpp
  • iFly/app/proto/sbus/sbus_protocol.cpp

底层原理

内部维护固定长度帧缓冲，持续从流式字节中找头字节和尾字节，重同步成功后再按 11 bit 布局解析出各通道值和标志位。

用到的技术

  • 流式缓冲与重同步统计。
  • 11 bit 通道的位级读写。
  • Parse() 与 Encode() 双向能力，便于独立测试协议栈。

代码阅读入口

  • 先看 Parse()，理解帧同步和多帧输出。
  • 再看通道位打包/解包逻辑，理解 11 bit 紧凑布局。
  • 最后看统计字段，理解后续如何做链路诊断。
当前状态

已实现但未接入主业务。协议能力已经具备，缺的是把它接到真实串口数据源和上层控制流程。

Receiver Protocol

CrsfProtocol

它负责 CRSF 串流拆包、CRC 校验、普通帧与扩展帧解析，以及 RC Channels Packed 的辅助编解码。

核心文件

  • iFly/app/proto/crsf/crsf_protocol.hpp
  • iFly/app/proto/crsf/crsf_protocol.cpp

底层原理

模块维护流式接收缓冲和预期包长，根据 length 字段决定当前帧完整长度，再做 CRC 校验和扩展字段解析。

用到的技术

  • CRC8 多项式 0xD5 校验。
  • 普通帧与扩展帧统一解析框架。
  • DecodeRcChannelsPacked() / EncodeRcChannelsPacked() 支持 RC 紧凑通道编解码。
  • 重同步和 CRC 错误统计，方便后续链路诊断。

代码阅读入口

  • 先看 Parse()，理解包长判断和 CRC 校验流程。
  • 再看 RC Packed 辅助函数，理解 16 路通道的紧凑打包方式。
  • 最后看统计字段和错误处理逻辑，理解协议栈健壮性设计。
当前状态

已实现但未接入主业务。和 SBUS 一样，它现在是协议模块完成态，不是整条接收机控制链路完成态。
